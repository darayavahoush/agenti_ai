# 2026-08-20: Migration rebaseline + schema drift cleanup

## What changed in code

- **`breathquest_refresh_tokens` table / `RefreshToken` model** — new
  table for revocable long-lived sessions, backing `POST /auth/refresh`
  and `POST /auth/logout`. Access tokens stay short-lived JWTs
  (unchanged); this is the other half that a JWT alone can't support
  (early revocation).
- **`locked_until` column fix** — was unmapped on `KidLoginThrottle`
  (a live DB column the ORM never wrote to) and stray-mapped on
  `RefreshToken` (copy/paste leftover from an adjacent class). Now
  mapped only where it belongs.
- **Removed `Base.metadata.create_all(bind=engine)` from `main.py`** —
  it was silently racing Alembic: it created `breathquest_refresh_tokens`
  itself, before the real migration for it ran, causing a
  `DuplicateTable` error the first time `alembic upgrade head` tried to
  create it too. Alembic is now the sole source of schema truth.
  **Fresh databases now require `alembic upgrade head`** —
  `create_all()` will no longer bootstrap one.
- **New migration root: `000baseline0`** — the old first migration
  (`a1b2c3d4e5f6`) assumed `create_all()` handled table creation and
  was never a true baseline; it only ever `ALTER`ed on top of that
  assumption. `000baseline0` was generated by diffing an empty Postgres
  DB against `Base.metadata` directly, and is the real root now.
  `a1b2c3d4e5f6.down_revision` was rewired to point at it.

## Local DB cleanup (NOT captured in a migration)

The following was done directly against the local dev DB via `psql`,
to bring it in line with what `000baseline0` assumes a fresh DB looks
like. It was **not** written as a migration, because as of this date
there is no staging/prod environment or other developer DB that needs
to reproduce it — only this local DB existed.

- Dropped 11 orphaned, non-`breathquest_`-prefixed legacy tables
  (`assignments`, `subscriptions`, `home_practice_logs`, `goals`,
  `email_verifications`, `voicehurdlerace_sessions`, `game_settings`,
  `retrain_checkpoints`, `parents`, `messages`, and the non-prefixed
  `rl_training_events`). Confirmed via grep that no current model
  class declares any of these tablenames. All were empty except
  `rl_training_events`, which had 2 real rows for an actual patient —
  those were migrated into `breathquest_rl_training_events` (same
  schema, same FK target) before the old table was dropped.
- `patients` table: dropped the dead, always-`NULL`,
  unreferenced-in-code `assessment_patient_id` column (distinct from
  `breathquest_patients.assessment_patient_id`, a different, actively
  used FK column on a different table — easy to conflate by name).
  Added the `registered_therapist_id → therapists.id` FK and index;
  verified existing data against `therapists` first, no orphans found.
- `flashcard_attempts.created_at` and
  `flashcard_phoneme_mastery.first_practiced_at` /
  `last_practiced_at` tightened to `NOT NULL`; confirmed zero existing
  `NULL`s first.

## ⚠️ Before stamping this baseline anywhere else

`000baseline0`'s docstring says: for an **existing, already-migrated**
database, run `alembic stamp 000baseline0` instead of
`alembic upgrade head` (upgrading would fail with `DuplicateTable`
against tables that already exist). But **stamping runs zero DDL** —
it only marks the revision as applied.

That means if this baseline is ever stamped against a database that
hasn't already had the cleanup above applied (a future staging/prod
DB, another developer's existing local DB), that database will be left
with the 11 legacy tables, the old `patients.assessment_patient_id`
column, and nullable flashcard timestamps — **permanently and
silently**, since nothing will error.

Before stamping `000baseline0` anywhere other than this machine: either
write a proper migration capturing the cleanup above, or manually
replay these same checks (see git history / chat log from
2026-08-20 for the exact `psql` commands and the data-safety checks
run before each one) against that database first.
